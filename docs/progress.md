- **Weekend 2 checkpoint reached: router + RAG node + order node working end-to-end with real multi-turn memory; escalation and auth stubbed.** All 5 routes verified individually and through the actual compiled graph, not just assumed.
- Re-taught LangGraph concepts (State/nodes/edges/conditional edges/checkpointers) and the two-level hierarchical router design from last session, then went deeper on one open question: **regex-only escalation gating is a real production anti-pattern**, caught via the user's own adversarial example ("these earbuds feel like fire" would falsely hard-route to ESCALATION). Researched how production systems actually handle this (web search, not assumed) — consistent pattern found: regex/keywords should be a *signal* fed into the LLM classifier's prompt, never a hard gate; confidence-banded escalation (auto-handle / auto-escalate / middle band) is the broader industry pattern, noted for later, not built yet.
- Decided the graph-level router needs **structured output** (`.with_structured_output()` + a Pydantic `RouterDecision` model with a `Route` enum of the 5 categories), not plain-string parsing like `classify_query` uses — reasoning: a malformed route string breaks a dict-based conditional edge (crash or silent misroute), a categorically worse failure than a slightly-off RAG filter.
- Verified via `tools/test_router_structured_output.py`: `qwen3:1.7b` + `.with_structured_output()` reliably returns schema-conformant output across 9 adversarial test cases (figurative "fire" language, real escalation, blended intent, Hinglish, sarcasm, hedged safety complaints, auth) — mechanism holds up.
- Found and fixed a real classification-quality bug this way (not a format bug): initial `PRODUCT_RAG` prompt description didn't cover recommendation requests or figurative/complaint language, so the earbuds case misfired to `FALLBACK`. Sharpened the category description, reran, fixed. Same pattern surfaced again on a sarcastic complaint ("explosive quality" as sarcasm) also misfiring to `FALLBACK` — noted, not yet fixed (deferred).
- **Blended-intent finding, deferred by design choice:** a message carrying two genuine intents (order status + product recommendation) only gets routed to one (`ORDER`), silently dropping the other. User's call: acceptable for now — noted as a real structural gap (schema forces exactly one route; would need `list[Route]` or a fan-out mechanism) rather than solved today.
- **Latency investigation, inconclusive but well-documented:** original 2026-07-04 baseline (`think:false` ~2-4s/call) no longer holds — observed 20-52s/call average even for `think:false` structured-output calls, with high run-to-run variance (14-78s for the same prompts). Ruled out structured-output overhead as the primary cause (plain-text calls were also slow, ~20s avg). Checked `ollama ps` (model loaded, 100% CPU, short keep-alive window) and `free -h` (severe memory pressure, 824Mi free, swapping) — closing memory-heavy apps (Chrome/Cursor/Postman) freed RAM (824Mi → 2.8Gi) but made timing *worse*, not better, pointing at CPU contention rather than RAM as the dominant factor. Root cause not conclusively identified — **explicitly flagged and deferred**, not treated as an architecture problem; doesn't change any design decisions made today.

- Visualized the compiled graph (`tools/visualize_graph.py` → `docs/graph/router_graph.mmd`, viewed via mermaid.live) — confirmed structure matches design: one router fanning out via conditional (dashed) edges to all 5 nodes, each converging to `__end__`.
